02 • BÀI TOÁN VẬN HÀNH THỰC TẾ Vì sao bể cá thủy sinh cần Real-time Operations?
🚨 Sự cố 1: Tắc nghẽn lọc tuần hoàn

Cặn hữu cơ và rêu làm nghẹt đường ống bơm lọc (Canister Bio-Filter / Sump) khiến lưu lượng tuần hoàn tụt từ 4.5 LPM xuống < 1.0 LPM và mực nước sụt mạnh.

Hậu quả: Nước mất dòng chảy & thiếu oxy hòa tan đột ngột → Cá ngạt trong vòng 1–2 giờ.
🧪 Sự cố 2: Sốc kiềm hóa pH (> 7.6)

Khi nước tù đọng hoặc vi sinh mất cân bằng, độ pH vọt lên > 7.6 – 8.2, chuyển hóa Amoni (NH₄⁺) vô hại thành khí độc Amoniac (NH₃).

Hậu quả: Cháy mang cá Neon Tetra, Guppy, chết san hô — người nuôi truyền thống chỉ phát hiện khi đã quá muộn.
🎯 Mục tiêu giải pháp: Biết sự cố trước khi cá chết • Điều tra nguyên nhân gốc trong 1 cú click • Đo lường tốc độ phục hồi (MTTR)

04 • KIẾN TRÚC DỮ LIỆU MONGODB ATLAS Database: smart_aquarium_iot
Schema chuẩn "One Reading, Three Parts"
{
  "ts": ISODate("2026-11-15T15:34:19Z"), // timeField
  "sensor": {                            // metaField
    "id": "AQUA-TANK-01",
    "zone": "Living Room 1F",
    "crop": "Neon Tetra & Guppy",
    "system_type": "Canister Bio-Filter"
  },
  "ph": 6.82, "ec_ppm": 400,             // measurements
  "water_temp": 25.0,
  "water_level_pct": 88.5,
  "pump_flow_lpm": 4.50
}
Tối ưu Time Series & Vòng đời dữ liệu
  • ✅ granularity: "seconds" — Nén bucket tối ưu cho nhịp 2 giây/mẫu.
  • ✅ expireAfterSeconds: 604800 — TTL tự động dọn dữ liệu quá 7 ngày.
  • ✅ Compound Indexes: [('sensor.id', 1), ('ts', -1)] & [('sensor.crop', 1), ('ts', -1)].
Collections Vận hành Bổ trợ
  • 📋 incidents: Lưu status (ACTIVE/RESOLVED), detected_at, resolved_at, mttr_seconds, trigger_reading, và dd_trace_id.
  • 🐠 devices: Danh mục cấu hình 3 bể AQUA-TANK-01/02/03.
Khởi tạo chuẩn xác qua scripts/setup_mongo.py Slide 4 / 10
05 • MONGODB AGGREGATION PIPELINES backend/app/analytics.py
1. Trạng thái Mới nhất
GET /api/telemetry/latest

$match theo ts ngay đầu pipeline để skip buckets, sau đó $sort: {ts: -1} và $group theo $sensor.id với $first để trả thông số tức thời của cả 3 bể.

2. Tổng hợp Theo Giờ
GET /api/analytics/hourly

Dùng $dateTrunc với unit: "hour" và timezone: "Asia/Ho_Chi_Minh" tính avgPh, minPh, maxPh, avgEcPpm, avgFlowLpm hiển thị tại trang /data.

3. Window Function Phát hiện Sớm
GET /api/analytics/trend

Dùng $setWindowFields (documents: [-4, 0]) tính trung bình trượt 5 mẫu gần nhất: movingAvgFlowLpm & movingAvgPh để nhận diện tắc lọc thật sự so với nhiễu tức thời.

$setWindowFields: { sortBy: { ts: 1 }, output: { movingAvgFlow: { $avg: "$pump_flow_lpm", window: { documents: [-4, 0] } }, movingAvgPh: { $avg: "$ph", window: { documents: [-4, 0] } } } }

07 • SỰ CỐ VẬN HÀNH: DETECT → INVESTIGATE → RESPOND Bể mục tiêu: AQUA-TANK-01
1. DETECT (Phát hiện)

Gạt công tắc Fault Switch trên Wokwi (hoặc bấm 🚨 Gây Sự Cố trên Web): Lưu lượng tụt 0.35 LPM, pH vọt 8.15.

→ LED đỏ sáng, Còi hú, OLED báo CLOG ALERT!, MongoDB mở incident ACTIVE, Datadog nổ P1 Alert.

2. INVESTIGATE (Điều tra)

Từ Datadog Alert mở Log [AQUA_ALERT] gắn rack_id:AQUA-TANK-01 & dd.trace_id; kiểm tra ingest.latency_ms bình thường để loại trừ lỗi DB.

→ Đồ thị MongoDB $setWindowFields tại /data xác nhận đường trung bình trượt Flow giảm dốc.

3. RESPOND (Phản ứng)

Bấm 🛠️ Xả Ngược & Cân Bằng pH trên Web (hoặc Datadog Webhook tự động kích hoạt /api/incident/respond).

→ ESP32 tắt còi/LED đỏ sau <0.2s, MongoDB đóng incident RESOLVED và gửi metric mttr_seconds lên Datadog.

⏱️ Toàn bộ chu trình từ lúc gạt lỗi → cảnh báo → điều tra → xả ngược → ghi nhận MTTR diễn ra trực tiếp trong < 30 giây!
